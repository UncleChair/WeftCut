# Render fixtures

Reference projects for the PixiJS renderer. Each fixture is a self-contained
directory the runner (`apps/desktop/src/render/fixtures/runFixture.ts`) can
load, drive through the export Worker, and compare against committed baseline
frames.

The fixture suite is the renderer's regression gate. **Per `docs/pixi-renderer-plan.md`,
PixiJS's own output is the ground truth** — there is no second renderer to
compare against. Baselines are generated by running the runner once, manually
inspecting the output, then committing the PNGs. Future PRs that touch
`apps/desktop/src/render/**` are expected to leave baselines unchanged or
intentionally re-baseline with a justification in the commit message.

## On-disk layout

```
fixtures/<NNN>_<name>/
  manifest.json     # Required. Fixture metadata + sample times.
  project.json      # Required. A serialized ProjectSummary (the same shape
                    # `useProjectStore.summary` carries at runtime).
  media/            # Optional. Media files referenced by media_id.
    <media_id>.<ext>
  expected/         # Baseline frames, one PNG per sample time. Generated
                    # by running the runner in "generate baselines" mode;
                    # not authored by hand.
    t_<microseconds>.png
```

The directory name's leading number determines fixture ordering in CI
output; the underscore-separated name is for humans. Numbers are not
load-bearing — the runner reads them from the dir listing alphabetically.

## manifest.json

```jsonc
{
  "name": "001_color",
  "description": "Single solid Color layer for two seconds.",
  // Composition dims. Should match project.json's composition.{width,height}.
  // Duplicated here so the runner can sanity-check before loading the project.
  "width": 1920,
  "height": 1080,
  // Sample times for baseline frames. Must be strictly increasing.
  // Each value is microseconds from composition t=0. The runner extracts
  // one frame from the encoded MP4 at each sample time.
  "sample_times_us": [0, 1000000]
}
```

## project.json

A snapshot of `ProjectSummary` (defined in `apps/desktop/src/ipc/index.ts`).
The simplest way to produce one is to author the project in the real app,
then dump `useProjectStore.getState().summary` to JSON. The fixture loader
treats this as authoritative — schema migrations should re-export to a v6
project.json when they land (P11).

`media_id`s referenced by layers must correspond to files in `media/`.
The runner synthesizes a `MediaSummary` per media item by reading the
file's bytes for width/height/duration extraction (image files via
`createImageBitmap`; video files via the same probe path the import
flow uses). Synthetic media-pool entries fill in:

- `path`: absolute path resolved from `<fixture_root>/media/<media_id>.<ext>`
- `kind`: derived from file extension
- `proxy_path`: null (the runner uses originals; the proxy job doesn't run)
- `available`: true

## Sample times

Pick sample times that exercise the layer's lifetime, not its boundaries.
For a 2-second layer, sampling at 0 and 1000000 (1s) catches the entry
state + steady state. Add boundary samples (e.g., 1999999) only when the
layer's behavior at end-of-life is what's being tested.

## Generating baselines (once per fixture)

There's no UI surface; baseline authoring runs from devtools. The
loop:

1. Boot the desktop app with the pixi preview enabled — append
   `?pixi=1` to the URL or set the localStorage flag in
   `apps/desktop/src/render/pixiPreviewFlag.ts`.
2. Open DevTools.
3. Run:
   ```js
   await window.__weftcut_generate_baselines(
     "C:/abs/path/to/apps/desktop/fixtures/001_color"
   );
   ```
   The runner executes the export Worker end-to-end, extracts a PNG
   at each `sample_times_us`, and writes them to `expected/`.
4. Visually inspect the PNGs. If they look right, `git add fixtures/<NNN>_…/`
   and commit. If not, fix the fixture or the renderer first, then
   re-generate.
5. Commit `manifest.json` + `project.json` + `media/*` + `expected/*`
   in one commit per fixture so future contributors can reproduce the
   baseline from source.

## Checking against baselines (every render change)

```js
// Single fixture:
await window.__weftcut_check_fixture(
  "C:/abs/path/to/apps/desktop/fixtures/001_color"
);
// → { pass, samples: [{ tUs, score, pass, expectedPath, … }] }

// Whole suite (every subdir of `fixtures/` with a manifest.json):
await window.__weftcut_check_fixture_suite(
  "C:/abs/path/to/apps/desktop/fixtures"
);
// → { pass, fixtures: [...] }
```

The compare is SSIM via the Rust `image-compare` crate
(`MSSIMSimple`), scores in [0, 1] where 1.0 is pixel-identical. The
pass threshold (`FIXTURE_SSIM_PASS_THRESHOLD` in `runFixture.ts`)
defaults to 0.995 — tight enough to catch real regressions (off-by-one
shifts, blend changes, dropped layers) but loose enough to absorb the
~bit-level noise between the canvas-rendered MP4 and the committed PNG.

A `missingBaseline: true` sample isn't a failure — it's a "run
`__weftcut_generate_baselines` once" signal for a fixture whose
`expected/` is empty.

## Binary-bearing fixtures (deferred)

Every shipped fixture today is purely synthetic — no `media/` files,
no woff2 fonts, no PNGs. That keeps the suite cheap to clone and free
of license tangles. Adding fixtures that exercise `VideoClip` /
`ImageOverlay` / `Subtitles` requires real media files in the repo,
which raises:

- **Size budget.** A 2 s `testsrc` H.264 is ~50 KB. A 1080p clip is
  larger. Crossing some threshold (a few MB per fixture? a total
  cap?) turns clone time + binary-diff churn into a real cost.
- **Reproducibility.** Anyone re-baselining locally needs the same
  exact bytes as committed. `ffmpeg testsrc` is deterministic given
  identical args, but encoder versions drift. Either we commit the
  resulting MP4 (binary-diffable but stable) or commit a script
  that regenerates it (small, but at the mercy of the host ffmpeg).
- **License / attribution.** Sample footage from elsewhere brings
  attribution obligations.

These trade-offs deserve their own decision before the first binary
fixture lands — flagged here so a future PR doesn't quietly ship one.

## CI-style gate (`npm run fixtures:check`)

The end-to-end flow that doesn't need a webview or DevTools:

```
# One-time, per machine (Playwright pulls Chromium ~150 MB):
npm install
npx playwright install chromium

# Every check:
cd apps/desktop
npm run fixtures:check
```

Under the hood the script:

1. Runs `npm run fixtures:render` — a vitest browser-mode test
   (`*.browser.test.ts`) drives the export Worker for each fixture
   and writes the resulting MP4 to `apps/desktop/build/fixtures/<name>.mp4`
   via a Node-side vitest command.
2. For each fixture, invokes `cargo run --bin fixture_compare --
   --fixture <root> --mp4 <build/fixtures/<name>.mp4>` — the Rust
   binary extracts a PNG per `sample_times_us` via ffmpeg, SSIM-compares
   against `expected/`, prints a JSON report, exits 0/1.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | All fixtures passed |
| `1` | SSIM regression OR hard error (decode failure, manifest unreadable, etc.) |
| `2` | Missing baselines — run `__weftcut_generate_baselines` to fill them in (or pass `--allow-missing-baseline` to ignore this class) |

### Flags

- `--skip-render` — assume `build/fixtures/*.mp4` already exist;
  skip the vitest render step. Useful when iterating on the compare
  half.
- `--allow-missing-baseline` — treat fixtures whose baselines aren't
  committed yet as passing. Default fails on them so a fixture
  without baselines doesn't slip into CI as a silent no-op.

### Why two halves

Render needs a real browser (WebGL + WebCodecs + Worker +
OffscreenCanvas). Compare is pure Rust. Splitting the pipeline at
the MP4 boundary keeps the moving parts independently debuggable
and lets CI cache the Playwright Chromium install across runs without
also caching ffmpeg / image-compare state.

### Per-fixture invocation

For ad-hoc runs against one fixture without re-rendering the rest:

```
npm run fixtures:compare -- \
  --fixture fixtures/001_color \
  --mp4 build/fixtures/001_color.mp4
```

Same flags as the wrapper; same exit codes.

## What lives outside a fixture

The fixture directory does NOT contain decoder caches, runtime logs, or
the encoded MP4. The runner produces these in memory + temp paths and
discards them after writing baselines or running the compare. A fixture
is reproducible from `manifest.json` + `project.json` + `media/` alone.
